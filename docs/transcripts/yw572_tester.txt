## Type normalization versus duplicate removal

**What differs.** The plan’s order is numeric coercion, then the missing-value check, then exact row equality, and only then the summary, which strips and lowercases `type`. Its hard errors are a missing column, an extra column, a non-numeric feature or `quality`, and any missing required value.

`run_pipeline` calls `validate_type` immediately after the column check, before numeric coercion and before `remove_duplicates`. That function rewrites `type` with strip and lower, then raises `Invalid type values:` for any other non-null label.

Two inputs therefore diverge:

- `Red` and `red` with the same measurements become one row. `duplicates_removed` goes up, and `rows_after_dedup`, `rows_modeled`, the summary count, and the train/test split all shrink. Under the plan both rows remain, and the summary groups them later.
- `rose` exits 1 and writes nothing. Under the plan that row stays and becomes its own summary group.

`summarize_by_type` already strips and lowercases. The early call is what changes duplicate identity. On `data/wine_quality_merged.csv` the published counts still match, so those cells are already `red` and `white`.

**Smallest correction.** Delete `frame = validate_type(frame)` from `run_pipeline`. Leave strip and lower only inside `summarize_by_type`. Remove `validate_type` and the tests that expect `Invalid type values:`. Remove the README sentence that says an invalid `type` stops the run. Do not add a new rejection, and do not edit `docs/plan.md` to match the extra check.

**Regression test.** Add `test_pipeline_keeps_type_case_variants_until_summary`:

- Start from `sample_wine_df` (12 unique complete rows).
- Append a copy of row 0, then set only that appended row’s `type` to `Red`. Row 0 stays `red`. Every other column matches.
- Run `run_pipeline`.
- Assert `duplicates_removed == 0`, `rows_after_dedup == 13`, and `rows_modeled == 13`.
- Assert `summary.csv` has one `red` row whose `count` is 7.

The current code fails this: both labels become `red` before `drop_duplicates`, so one row is removed and the red count stays 6. A count of 7 shows the rows survived dedup and were grouped only in the summary.
